# Как ставить задачу агенту

Источник: доклад «Eight Steps · Multi-Agent Development», Куаныш Сейлханов, HackAlem.
Плюс первоисточники: OpenAI Codex team, Anthropic, Thoughtworks, Bun, Cognition.

## Рамка: агент = модель + обвязка

Обвязка делится на две половины, и нужны обе:

- **Guides — действуют до.** Промпт, этот свод правил, скилл. Говорят, что делать.
- **Sensors — действуют после.** Тесты, линтер, ревью-субагент. Проверяют, что вышло.

Только guides — агент никогда не узнает, сработали ли правила. Только sensors — он повторяет те же ошибки.

Про любой кусок обвязки полезно спросить: он действует **до**, чтобы направить, или **после**, чтобы поймать?

Ключевое ограничение: **чего агент не видит, того не существует.** Решение, принятое в разговоре или в голове, для него невидимо.

## Шаг 1. Сказать, что значит «готово»

Каждая постановка задачи называет четыре части:

```
GOAL    что должно получиться — не как делать
WHERE   два-три файла, которые имеют значение
LIMITS  что трогать нельзя
DONE    проверка, которая должна пройти —
        её называешь ты, пишет агент
```

Плохо: `добавь удаление расхода`

Хорошо:
```
GOAL   расход удаляется из списка, итог и суммы по категориям пересчитываются
WHERE  src/core/expenses.js, src/ui/list.js
LIMITS не менять формат хранения, не добавлять зависимости
DONE   npm test зелёный, включая новый тест:
       удалили расход 900 → итог 2100, еда 1500
```

Тридцать секунд лишнего набора. **Чаще всего пропускают `DONE` — а это именно то, что позволяет агенту доработать задачу без тебя.**

## Шаг 2. Верификация

> «Важно, чтобы верификатор задачи был почти идеальным, иначе модель решит не ту задачу.»
> — Николас Карлини, Anthropic, после сборки компилятора C силами 16 агентов

- Агент, работающий один, не может переспросить. **Тест становится задачей.**
- Что проверяет тест — говоришь ты. Пишет его агент. Ты читаешь этот один тест.
- На хакатоне: **три теста, только тот путь, который будешь показывать.** В первую очередь — контрольный пример из ТЗ.

## Шаг 3. Ревью — отдельным агентом

Автор — плохой проверяющий: он одобряет собственную работу.

> «Claude, который написал код, хочет, чтобы код приняли. Claude, который ревьюит, хочет найти в нём проблемы.»
> — команда Bun, переписывание миллиона строк с агентами

Как давать задачу проверяющему:

- **Только диф.** Не весь файл и не историю рассуждений.
- **Установка: считай, что код неверный.** Вежливый промпт получает вежливое «да».
- **Одна работа: найти причины, по которым это не работает.**
- Несколько проверяющих сразу, каждому свой угол: корректность, безопасность, простота.

Их правило, добавленное после того, как агенты начали прятать проблемы в комментариях:
«Если для оправдания обходного решения нужен абзац комментария — код неверный, чини код».

## Шаг 4. Длинная сессия портит качество

Четыре часа в одной сессии — качество падает, агент начинает терять нить.

**Лечение:** записать три строки о том, где ты сейчас, **в файл в репозитории**, и начать новую сессию.
Свежая сессия читает файл, а не старую переписку.

## Шаг 5. Много агентов — только если файлы не пересекаются

- **Безопасно:** несколько агентов **читают** одно и то же. Три ревьюера на один диф — втрое быстрее, конфликтовать нечем.
- **Опасно:** несколько агентов **пишут** в одно место.

Карлини запустил 16 агентов на компилятор: они разлетелись по отдельным падающим тестам, а потом все шестнадцать упёрлись в один и тот же баг и **стёрли правки друг друга**. Починил не агентов, а раскладку — **один файл на агента**.

Правило: **один агент пишет — одна зона. Читать могут многие.**

## Пять способов проиграть

1. **Вайб-мёрдж.** 900 строк, которых никто не читал, потому что «выглядит нормально».
2. **Слишком быстро.** Много агентов до того, как появилась проверка. Самая частая хакатонная ошибка.
3. **Слишком много.** Просил починить — получил переписывание. Лечится строкой `LIMITS`.
4. **«Потом почистим».** Старый код остаётся рядом с новым, с комментарием-обещанием. Удалять сразу.
5. **Длинная сессия.** См. шаг 4.
