# Красные линии — развёрнуто

Нумерация — по **редакции Положения от 22.09.2026** (17 разделов переписаны в 6, нумерация вложенная).
Нарушение любого пункта обнуляет всю работу независимо от качества кода.

1. **Промежуточный результат за каждый отчётный час** (5.4.8). Засчитываются изменения в коде или репозитории, функционал, прототип, дизайн, схема архитектуры, настроенная модель, проведённое тестирование, подготовленные данные. Отсутствие подтверждённого результата за любой отчётный час — основание для дисквалификации (5.9.2). Рабочая норма: содержательный коммит и пуш минимум раз в 30 минут.
2. **Разработка только в репозитории организатора** (5.4.9, 5.4.11). «Использование сторонних закрытых репозиториев для основной разработки, хранения кода Проекта либо передачи финальной версии не допускается.» В репозитории должна остаться подтверждаемая история — её отсутствие отдельное основание для дисквалификации (5.9.2).
3. **Разработка только на площадке** (5.1.7). После check-in участник не вправе покидать территорию и вести разработку вне площадки. Временный выход — только с предварительного разрешения, **суммарная продолжительность отсутствия не более 60 минут** (5.1.7.1); превышение без согласования — основание для дисквалификации. Лимит не применяется при экстренных обстоятельствах по списку 5.1.7.2 (здоровье, медпомощь, чрезвычайные семейные обстоятельства, безопасность) с обязанностью уведомить Организатора при первой возможности.
4. **Проект должен запускаться по README** (5.4.16, продублировано в 5.6.5). «Если итоговую версию Проекта не удаётся запустить по инструкциям, размещённым в Репозитории, Команда не допускается к дальнейшему отбору. Дополнительные пояснения и исправления не принимаются.» Это условие допуска, а не критерий с баллами.
5. **Проверка без личных аккаунтов** (5.6.6). Ключевая функциональность проверяется без личных аккаунтов участников, персональных подписок и закрытых учётных записей. При использовании внешних сервисов и API команда обязана предоставить демонстрационные доступы, тестовые учётные записи либо иной способ проверки.
6. **Раскрытие стороннего** (5.4.4). Раскрывать открытый исходный код, библиотеки, модели, датасеты, шаблоны и иные сторонние компоненты. Open-source сам по себе не нарушение (5.4.4.1); нарушение — использование существенных частей чужого решения без раскрытия источника либо выдача его за своё.
7. **Заранее подготовленное ограничено** (5.4.4.2, 5.4.5). Свои библиотеки, шаблоны и инфраструктурные решения допустимы, если не являются готовым продуктом или основной частью решения. «Основная функциональность Проекта, соответствующая Задаче, должна быть разработана в рамках Соревновательной части.» Подавать ранее созданный готовый продукт нельзя. Наш каркас и свод правил под запрет не подпадают — это процесс, а не функциональность; но в README их стоит назвать, чтобы вопрос не возникал.
8. **Права на материалы** (6.1.5, 6.1.7). Только то, на что есть законные права и совместимая лицензия.
9. **Окончание — 18:00** (5.4.13). Итоговой признаётся версия на этот момент «независимо от момента фактической блокировки интерфейса платформы». Изменения после окончания не учитываются (5.4.14). Финальный пуш — с запасом.
10. **Никаких скрытых инструкций для AI-судьи.** Организатор вправе применять автоматизированные системы как вспомогательный инструмент предварительного анализа и ранжирования (4.2–4.4).
11. **Codex.** Положение (5.4.12) говорит, что Codex не обязателен. Лендинг hackalem.ai в разделе «Кто может принять участие» требует дословно: «Во время хакатона команда должна использовать Codex в процессе разработки» — проверено 22.09.2026. Исходим из обязательности: применять к реальным задачам и отметить в README.
12. **Сдача — отдельная форма на платформе.** Название проекта, описание, теги, ссылка на презентацию и ссылка на видео-демо. Обязательность презентации и видео задаётся организатором для каждого кейса отдельно. Форма разблокируется только после отметки о присутствии и при созданной команде. Проверить в начале работы.

## Как оценивают

**Общей таблицы критериев больше нет.** Пять критериев прежнего п. 7.4 в редакции от 22.09 отсутствуют полностью.

- **Критерии — только из ТЗ задачи** (5.5.1–5.5.3). ТЗ каждой задачи самостоятельный документ со своими требованиями, способами проверки, критериями и распределением баллов.
- **Критерии публикуются до начала соревновательной части** (5.5.3): «применяются исключительно условия и критерии, опубликованные для соответствующей Задачи **до начала Соревновательной части**». Искать их утром 23.09, до 13:00; опубликованное позже применяться не может.
- **Выбор задачи перестал быть нейтральным.** Прежняя гарантия, что предметная область, популярность задачи и число решающих её команд сами по себе не влияют на оценку, из текста убрана. П. 5.5.4 разрешает «приведение результатов к единой шкале, нормализацию, ранжирование либо иной способ сопоставления результатов» между задачами.
- **Порядок отбора финалистов** определяется Организатором и доводится через официальные каналы (5.6.7). Прежней процедуры тай-брейка комиссией из трёх экспертов большинством голосов больше нет; решение принимается Организатором с учётом заключения экспертов и оформляется протоколом.
- Термин «обязательные условия допуска» в тексте сохранился (5.6.7), но больше нигде не раскрыт и обязанности публиковать их отдельно нет.

**Знание о платформе (не из Положения, проверено по её интерфейсу):** критерии задаются для каждого кейса отдельно; итоговый балл считается как среднее по судьям **с учётом весов критериев**, плюс отдельное поле «бонус организатора». Открывать вкладку «Критерии оценки» самого кейса.

**Ориентир по форме кейсовой шкалы** — ТЗ пробного запуска «Учёт личных расходов студента»: работающий сценарий 30, точность расчёта 30, надёжность 15, удобство 15, сдача 10. Там же оговорка: дополнительные возможности «не повышают максимальный балл». Проверять эту оговорку в своём ТЗ первым делом.
