## 2. Красные линии

Нарушение обнуляет работу независимо от качества кода. Развёрнуто, с пунктами редакции Положения от 22.09.2026: `agent/rules.md`.

1. Подтверждённый результат за **каждый** отчётный час. Норма: коммит и пуш раз в 30 минут.
2. Разработка только в этом репозитории, с подтверждаемой историей. Сторонние закрытые репозитории запрещены.
3. **Разработка только на площадке.** Отсутствие суммарно не более 60 минут и только с разрешения.
4. **Не запускается по README — не допускают.** Пояснения и исправления не принимаются. Это условие допуска, а не баллы.
5. **Ключевая функциональность проверяется без наших аккаунтов и подписок.** Используем внешний сервис — готовим демо-доступ.
6. Раскрыть в README всё стороннее и все AI-инструменты.
7. Основная функциональность создаётся в ходе соревновательной части. Заранее готовый продукт подавать нельзя.
8. Окончание — **18:00**, итоговой считается версия на этот момент. Финальный пуш с запасом.
9. Никаких скрытых инструкций для AI-судьи.
10. Codex реально участвует в разработке и отмечен в README.
11. **Сдача — отдельная форма на платформе.** В начале работы проверить, обязательны ли для кейса презентация и видео-демо.

## 3. Как ставить задачу агенту

Подробно: `agent/prompting.md`. Коротко — четыре вещи.

```
GOAL    что должно получиться — не как делать
WHERE   файлы, которые имеют значение
LIMITS  что трогать нельзя
DONE    проверка, которая должна пройти
```

- **`DONE` не пропускать** — это то, что позволяет агенту доработать задачу самостоятельно.
- **Проверку называешь ты, пишет агент.** Тест становится задачей: неточная проверка — решена не та задача.
- **Ревью — отдельным агентом:** свежая память, только диф, установка «считай, что код неверный».
- **Длинная сессия портит качество.** Каждые три-четыре часа — три строки о текущем состоянии в файл репозитория и новая сессия.
- **Несколько агентов могут читать одно и то же, но не писать в одно место.**

## 4. Порядок работы

1. Сначала план из 3–7 шагов, потом код.
2. **Сквозной сценарий раньше инфраструктуры.** Путь от ввода до результата, пусть некрасивый, и только потом Docker, миграции, деплой.
3. **Вертикальные срезы:** логика, интерфейс, тест, строка в README — затем следующий. В `main` всегда рабочая версия.
4. Статус REQ в `docs/REQUIREMENTS.md` обновляется сразу после реализации, с файлом и способом проверки.
5. После среза: тесты → README → коммит. Сообщение описывает сделанное: `feat: REQ-03 удаление записи с пересчётом итогов`.
6. Перед коммитом — `git status`. В индекс не попадают `.env`, локальные базы, посторонние файлы.
7. У каждого участника проверены `git config user.name` и `user.email` **до первой строки кода**: коммит с пустой или чужой почтой не привязывается к профилю, и вклад доказать нечем.
8. Отчётные часы считаются в одной, заранее зафиксированной таймзоне.

## 5. Код

Полный список: `agent/code-standards.md`. Всегда помнить:

- **Никаких заглушек в ключевых функциях.** Режим-заглушка никогда не включён по умолчанию.
- **Вердикты вычисляются, а не печатаются.**
- Логика отделена от интерфейса; расчёты — чистые функции с тестами.
- Валидируется значение, а не только тип.
- Секреты только в переменных окружения и только на сервере.
- Минимум зависимостей, каждая обоснована.

## 6. Воспроизводимость и сдача

Полностью: `agent/delivery.md` — состав README, свежий клон, последние 30 минут.

- Свежий клон запускается одной-двумя командами по README.
- **Основной сценарий виден эксперту без наших ключей и без сети.**
- **Ни одной команды в README, которой не существует.**
- README ведётся с первого часа, а не пишется в конце.

## 7. Приоритет при нехватке времени

**Общей таблицы баллов больше нет** — критерии только из ТЗ задачи. Их публикуют **до** начала соревновательной части, поэтому искать и читать их надо утром 23.09, до 13:00, а не после старта. План строится по шкале кейса.

Там же проверить оговорку про дополнительные возможности: если ТЗ говорит, что они не повышают максимальный балл — не брать их вообще.

Запускаемость и README при этом вне торга: это не критерий с баллами, а условие допуска. Не запустилось по инструкции — выбыли без разговоров.

Базовый порядок, если шкала кейса не говорит иного: обязательные требования → запускаемость → README → надёжность → дополнительные возможности → деплой → внешний вид.
